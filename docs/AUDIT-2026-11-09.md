## 0. 结论先行

**代码的完成度远高于产品的完成度。** 前端状态机、三层缓存、空/错/加载三态、文本截断、ARIA 状态维护、reduced-motion 双端照顾都超出一般个人项目水准；`npm test` 30 项全绿，`npm run check` 通过。

但按「能不能作为一个最终产品交付给普通用户」来衡量，**当前版本不可发布**，有四类硬阻断：

| # | 阻断项 | 性质 |
|---|---|---|
| 1 | 默认把无鉴权的完整 API 暴露到局域网，且明文凭据以 644 落盘 | 安全 / 账号 |
| 2 | 音频流每 20 秒被强制切断；上游 URL 与 302 目标零校验（SSRF） | 核心功能 / 安全 |
| 3 | 小程序是 http + 内网 IP + 端口 + 游客 AppID，体验版/正式版必被拦截 | 平台合规 |
| 4 | 音源链路实际站位与产品规划自己选定的合规路径 A 不一致；无版权授权、无备案域名 | 法律 / 商业化 |

一句话判断：**这是一个「本机自用、自己懂 Node、接受手工排障」时相当好用的技术作品，但还不是一个有明确用户、可分发、可上线、可持续维护的产品。** 网站与小程序目前是「两个各自为战的客户端 + 一个无状态、无鉴权、无用户体系的本地代理」，不是「双端并行的产品」。

## 2. P0 安全漏洞

### 2.1 默认局域网暴露 + 零鉴权（实测确认）
`server/index.js:229-295` 主动探测非回环 IPv4 并再起一个 `http.createServer(handleRequest)`，注释写明「真机预览」，**没有任何开关可关闭**。`handleRequest`（:242-262）完全信任 `Host` 头，不校验 `Origin`/`Sec-Fetch-Site`，无 token、无 CSRF 防护。

叠加后果：同网段任何设备可调用全部接口、读取网易云账号资料（`/api/user`）、`POST /api/logout` 强制登出、反复拉流、刷二维码接口。这不是理论风险——本机实测 health 已显示 `logged:true`，即**当前磁盘上就有可用的 `MUSIC_U`**。

值得注意的是 `踩坑与复利.md:190` 自己写着「**必须绑 127.0.0.1**，包默认 0.0.0.0 会把无鉴权接口暴露到局域网」，而主服务随后在小程序真机预览需求下又做了一次双绑定。已知教训没有被固化成防护。

### 2.2 上游 URL / 302 目标零校验 → SSRF
`server/netease.js:392-427` 匿名分支 `redirect:'follow'` 后直接取 `res.url`；登录分支（:344）直接用上游 JSON 的 `data.data[0].url`，`toHttps()` 只替换协议头不做主机校验；`proxyAudio`（:430-478）再次 `redirect:'follow'` 并把响应体回显客户端。

只要上游被污染/劫持、`NETEASE_API` 指向不可信代理、或 302 指向 `http://127.0.0.1:*` / `169.254.169.254`，后端即代为请求并回显响应。`finalUrl` 还被缓存 10 分钟（`config.js:18`），一次污染影响后续所有该 id 请求。配合 2.1，可从局域网远程触发。
另 `isAudio` 用 `/audio/i` **子串**匹配（:449），`text/html; audio=1` 即可通过，文档承诺的「必须是 `audio/*`」不成立。

### 2.3 凭据生命周期全链路失守
| 位置 | 问题 |
|---|---|
| `netease.js:12,28` | `MUSIC_U` 明文写 `server/.login-cookie`，未指定 `mode:0o600`；实测文件权限 `-rw-r--r--`（644），842 字节 |
| `netease.js:98` | cookie 拼进上游 **URL query**，落入访问日志/代理日志；默认上游是明文 `http://127.0.0.1:3000` |
| `netease.js:337-339` | 上游返回 `-462/301`（常为临时风控）即 `setRuntimeCookie('')` → `rmSync` 删除用户凭据，一次普通取流就可能静默清空登录态 |
| `netease.js:16,527-530` | `runtimeCookie` 初值取自常量 `COOKIE`；用 `NETEASE_COOKIE` 启动时退出后**重启即复活**，且 `loginState()` 会同时返回 `logged:false` 与 `source:'env'`，自相矛盾 |
| `netease.js:30-32` | 删文件失败被 `catch` 完全吞掉，内存已清、磁盘仍在，无任何提示 |
| `netease.js:527-530` | 退出不通知上游 `/logout`，云端 `MUSIC_U` 仍有效，泄露后无法失效 |
| `index.js:198-206, netease.js:496-498` | 二维码创建/轮询用 GET、无限流、无并发上限，key 不绑定本服务会话；任意网页 `<img src="http://127.0.0.1:8787/api/login/qr">` 即可刷上游配额 |
| `index.js:207-210` | `POST /api/logout` 是 CORS 简单请求，无 `Origin`/`Content-Type`/token 校验 → **CSRF 强制登出** |

### 2.4 安全头不全
`server/index.js:45-46`：`media-src 'self' https: http:` 允许任意明文 HTTP 媒体（实际音频全走同源代理，`http:` 完全无必要）；`style-src 'unsafe-inline'`；缺 `object-src 'none'`、`frame-ancestors`（可点击劫持）。更关键的是 `SECURITY_HEADERS` 只加在 `sendJSON`/`serveStatic`，**`proxyAudio` 的 200/206 响应不带任何安全头**（`netease.js:463-472`），与 `docs/API.md:3`「所有响应带 CSP」不符。

## 3. P1 功能性 Bug（代码确认 / 可复现）

### 播放核心
1. **音频 20 秒必被截断** — `netease.js:437`。实测 `AbortSignal.timeout` 在响应体阶段抛 `TimeoutError`，`pipeline`（:477）中断 → `sendError` 见 `headersSent` 直接 `res.destroy()`（index.js:65-68）。一首 3–5 分钟的歌在第 20 秒断流，浏览器需重发 Range 续传，表现为周期性卡顿/重缓冲；不支持续传时直接播放中止。与 README:10「流式转发、可正常拖动进度」冲突。
2. **Range 处理不完整** — `netease.js:431,440,448`：`Range` 原样透传不校验；上游 `416` 被判为 `NO_AUDIO 404`，文档承诺的 `206/416` 中 416 永不出现。
3. **上游故障伪装成「无版权」** — `netease.js:354-357` 把网络/超时/5xx 一律转成 `no_copyright` → `NO_AUDIO 404`，前端「连续 3 首失败停止」逻辑被误导，用户以为歌没版权。登录态下 `levelChain` 最多 4 档 × (9s 超时 + 1s 重试)，最坏约 76 秒才有结论。
4. **登录态音频绕过本地代理** — `netease.js:344` 直接返回 CDN 直链给 `<audio>`，与 README/ARCH「音频由本地后端转流」不符，形成两条语义不同的播放链路。
5. **未知参数静默吞掉** — `index.js:162-163`、`netease.js:319-323`：非法 `level` 静默降级 standard，`fee` 任意数值透传，前端以为点了无损实际拿标准。
6. **权限门禁在客户端** — `getTrackUrl` 靠前端传的 `fee` 判断 VIP（`index.js:162`），`踩坑与复利.md:227-234` 已记录过「两端各写一份门禁必然漂移」（fee 8 事件），但架构上仍未收敛到服务端。

### 登录与 UI 状态
7. **空白二维码被伪装成「等待扫码」** — 后端 `netease.js:485` 用 `keyData?.code` 兜底当 key，上游缺 `unikey` 时 `key=200` 通过校验、拿到空 `qrimg`；前端 `login.js:141` 把 `qrImg.src` 设为 `''` 后仍 `setStatus('等待扫码…')`（:142）。用户看到破图却一直被要求扫码。
8. **登录态判定用本地缓存，默认筛选会错** — `login.js:45-47` 的 `isLogged()` 只读 `localStorage.pt_login.nickname`；`nav.js:53-67` 的 `initFilterDefault()` 在 `initLogin()` 的异步 `getLoginStatus()`（`login.js:194-210`）返回**之前**就执行。服务端登录态失效而本地昵称还在时，默认关闭「只看可播放」，用户看到满屏点不动的 VIP；异步回调纠正 state 后不会重新计算筛选（`filterAutoTuned` 已置 true，且无 `login:changed` 订阅）。
9. **「播放全部」绕过「只看可播放」筛选** — `nav.js:299-305` 用 `store.playlist`（`renderData:132` 存的是**全量**），而界面渲染的是 `playableList()` 过滤后的列表。筛选开启时点「播放全部」会立刻连播被隐藏的 VIP 歌并触发连续失败跳歌。同理 `nav.js:253-255` 在搜索结果页切筛选会 `loadView` 回原板块，搜索结果直接丢失。
10. **轮询播报刷屏** — `login.js:122-124` 网络波动时每 2 秒写一次 `statusEl`（`index.html:38` 带 `aria-live="polite"`），读屏持续打断。
11. **音量事件重复写盘** — `player.js:573-578` 的 `volumechange` 每次都 `saveSettings()`，与 `setVolume` 的 350ms 防抖（:392-395）叠加，拖动时仍频繁写 localStorage。
12. **`/api/health` 的 `cookie` 字段误导运维** — `index.js:133` 返回的是 `Boolean(COOKIE)`（仅环境变量），实测 `cookie:false` 而 `login.logged:true`。踩坑日志:211 明确要求「重启后必查 health 确认没有静默降级」，这个字段会给出错误答案（真正该看的是 `upstream` + `login`）。

### 小程序（详见第 5 节）
13. **双 `onLaunch` 覆盖** — `app.js:19-27` 与 `:60-62` 同名，后者生效，`wx.getStorageSync('playMode')` 永不执行，用户上次的随机模式冷启动后丢失。30 项测试全绿却没抓到，因为测试桩只验证了音频回放路径。
14. **`__loaded` 死代码** — `pages/index/index.js:55` 判断的字段全项目无赋值，扫码登录后切回小程序不刷新登录态，必须冷启动。
15. **连续失败后 UI 说谎** — `app.js:220` 直接赋值 `globalData.status='idle'`，绕过 `_setStatus` 不 emit，页面仍显示「正在播放」。
16. **总时长可能恒为 0:00** — `app.js:53-56` 只信 `audio.duration`；`/api/audio` 是流式转发无 Content-Length，列表里明明有准确 `track.duration` 却不兜底（`player.wxml:56` `max="{{duration || 1}}"`），进度条拖不动。
17. **`wx:key` 写错** — `player.wxml:32` 用 `wx:key="time"`，而解析结果是 `{ t, text }`（`utils/api.js:65-68`），列表复用告警、歌词可能错行。
18. **触屏拖拽把手是死 affordance** — `queue.js:153` 注释称「触屏仍可用上下移」，但全项目 Grep 无 `moveUp/moveDown` 实现，`⠿` 把手在触屏可见却不可用（同一误导也存在于小程序 `player.wxss` 队列）。

### 启动脚本
19. **`stop-server.bat` 误杀无关进程** — 实测见第 1 节，`:8/:14` 端口子串匹配 + `taskkill /F`（:11/:17）。同时 `/F` 强杀使 `server/index.js:303-304` 的优雅退出永不执行。
20. **启动判定不可靠** — `start-server.bat:16/:38` 同样子串误匹配会误判「服务已在运行」；`:54` 的 `curl -s` 无 `-f`/`--max-time`，HTTP 502 也算「健康检查通过」；`:6` 只查 node 存在不校验 ≥18；端口已在跑时直接开页面（:39-43），**不验证该进程是否指向本地上游**——正是踩坑日志:206-213 记录的「环境变量丢失静默回退公共代理」没被固化成防护。

## 4. 小程序：当前不能上线，也不能给普通用户用

**四条硬阻断（P0）**

1. `miniprogram/utils/api.js:4-8` 的 `BASE` 写死 `http://192.168.4.12:8787`（明文 http + 内网 IP + 端口）。微信合法域名强制 https + 已备案域名，且不支持配 IP/端口/localhost。
2. `app.js:159` 音频 `src` 共用同一非法 BASE，列表侥幸加载出来也放不出声。
3. `miniprogram/project.config.json:7` / 根 `project.config.json:6` / `project.private.config.json:5` 三处写死 `"urlCheck": false`，只在开发版生效，掩盖了上述两条。
4. 两份工程配置冲突：`miniprogram/project.config.json:3` 是占位 `touristappid`，根 `project.config.json:25` 才是真 AppID 且 `:19` 有 `miniprogramRoot`；而 `miniprogram/README.md:12` 却要求「目录选择 miniprogram」。按 README 导入无法上传/真机预览。

**平台适配**：`app.json:13` 声明 `requiredBackgroundModes:["audio"]`，但 `app.js:41` 用 `wx.createInnerAudioContext()`——后台/锁屏播放必须用 `wx.getBackgroundAudioManager()`（必填 `title`）。切后台即停、锁屏与线控全缺失，声明与实现不符还有审核风险。未监听 `wx.onAudioInterruptionBegin/End`，来电后状态不同步。

**能力对照（约为 Web 端 1/3）**：有榜单/播放/歌词/队列；缺搜索（`search()` 定义但零调用）、扫码登录与退出、评论、相似推荐、收藏/历史、音质、音量、后台/锁屏、离线缓存、暗色模式。`utils/api.js:39-46` 的 SECTIONS 还漏了「新歌榜」，且 `cat_学习` 标题在服务端/网页/小程序三处各不相同。

**共享登录态**：`utils/api.js:34-35` 注释明说「服务端共享登录态：网页版扫码后小程序直接可用」。后端无鉴权、无用户隔离——一旦按 README 把后端公网化，任何能访问该域名的人都在用同一个网易云账号听 VIP、看收藏。这既不是产品规划里的「用户自有账号」，也有账号被封风险。

**最短补齐路径**：统一工程入口与 AppID → 后端公网化（备案 https + 鉴权）→ BASE 配置化 → 换 `getBackgroundAudioManager` → 改走 `/api/track/:id/url` 门禁接口 → 修 4 个必修 bug（双 onLaunch / `__loaded` / 状态 emit / `wx:key`）→ 隐私指引与 `wx.requirePrivacyAuthorize` → 用**体验版（开合法域名校验）**跑完整真机验收。

## 5. 使用者视角：美学、动效、无障碍、响应式

### 三处系统性问题（P1，观感/可用性直接受损）
1. **四个 `role="dialog" aria-modal="true"` 全无焦点陷阱** — `index.html:26,45,63,291`。仅 `immersive.js:59-82` 做了焦点保存/恢复；`queue.js:103-113`、`login.js:149-163`、`shortcuts.js:11-22` 打开不移入焦点、关闭不恢复、底层未 `inert`。键盘用户 Tab 会跑到底层继续操作。

## 6. 最终产品层面（最该先想清楚的，不是代码问题）

### 6.1 合规站位与自己的产品规划冲突
`产品规划.docx` 3.2 明确列了三条路径并给出结论：**选路径 A**（用户扫码登录自己的账号，播放器只是「官方客户端的优雅替代前端」），3.3 进一步要求「**用户必须登录自己的账号**」「UI 上不出现破解/免费听歌字样」，路径 C（爬取/破解音源、无需登录）标注「极低，违法风险大，❌ 不推荐」。

而实现是：`README:10,59-60` 明确「匿名模式下免费歌可播、VIP 登录后播」，`netease.js:379-389` 匿名直接走 `music.163.com/song/media/outer/url` 外链抓流，登录是**可选增强**；小程序端更是「服务端共享一个登录态」。这实际站在「无需登录即可播放」的一侧，与路径 A 的强制登录要求不一致，也不是路径 B 的官方授权。

放大到产品层面：
- **小程序提审**：音乐/音频类目需版权授权或相应资质，第三方抓取网易云音源是常见驳回理由；当前连合法域名、备案、隐私指引都不具备。
- **网站公开部署**：同样的版权/服务条款风险，且会显著放大 2.1 的暴露面。
- 规划自己已把路径 A 的合规性标注为「中等（个人使用灰色地带）」——**目标定位本就应是个人开源/学习作品**。若定位如此，就应把「不分发、仅本机、强制自登录、明确免责」做实；若要成为面向公众的产品，路径 B（官方开放平台授权）是唯一可持续选项。这个决策不解决，后面所有 UI 打磨都不改变产品能否存在。

### 6.2 交付形态不是「产品」而是「开发脚本」
普通用户要用起来，需要：安装 Node ≥18 → 双击 bat → 保持两个黑窗口常开 → 电脑不关机 → 手机与电脑同 WiFi → 手动把 `BASE` 改成当前内网 IP → 在开发者工具勾「不校验合法域名」。`踩坑与复利.md:170-213` 里坑 13/16 反复记录「服务随会话消失、环境变量丢失导致静默回退」，说明这个痛点已在真实使用中反复发生，但一直靠「排障口诀」而非产品化手段解决。

产品规划 6.1 选的是 **Tauri 2 桌面应用**（安装包 2–20MB、系统托盘、开机自启、SQLite），实际交付的是「无构建网页 + 两个 Node 进程 + .bat」。`autostart-server.bat` 是唯一的「系统集成」，还硬编码路径。这一层差距决定了它目前只能是开发者自用工具。

### 6.3 规划与落地分叉（不是「没做完」，是「做了另一个产品」）
| 规划 | 实际 |
|---|---|
| Tauri 2 + React 19 + TS + Tailwind + Framer Motion + SQLite | 原生 HTML/CSS/ES Modules + Node 零依赖 + localStorage |
| 桌面端 Windows/macOS、系统托盘、全局快捷键、Toast 通知 | 浏览器网页 + 半可用小程序 |
| **P0 核心差异化：网易云 / QQ 音乐双源切换、歌单导入** | 网易云单源，无源适配层 |
| P0 播放模式：顺序/随机/单曲循环/列表循环 | 仅随机开/关 |
| P1 本地歌单、桌面歌词、翻译歌词、设置中心、缓存管理 | 部分（收藏/最近播放/歌词翻译），歌单与设置中心无 |
| P2 亮/暗主题、封面取色 | 暗色分支存在但被硬编码色破坏 |
| 明确不做社交/评论 | 做了热门评论 Tab |

规划里的**差异化全部落空**，剩下的是一个「能听免费歌的本地网页播放器」，可替代性极高。作为技术练习无可厚非，但作为产品需要重新回答「用户为什么不用官方客户端」。

### 6.4 「网站和小程序并行」目前没有共享层
- 数据：收藏/历史/队列/设置全在 Web 的 localStorage（`state.js`、`storage.js`），小程序只存 `playMode`（还因双 onLaunch 失效）；两端数据完全不通。
- 账号：后端单例 `runtimeCookie`，无用户体系、无隔离；Web 与小程序共用同一个网易云账号。
- 契约：`SECTIONS` 在 `server/config.js` 与 `utils/api.js` 各写一份且已漂移；LRC 解析在 `src/core/lyrics.js` 与 `utils/api.js` 各写一份、能力不等；`docs/API.md` 与实际返回结构多处不符。
- 结论：这是「两个客户端 + 一个代理」，不是「双端产品」。要真并行，至少需要一份共享的契约/常量包 + 服务端用户态与数据持久化。

### 6.5 质量保障是「假绿」
`npm test` 30 项全通过，但只覆盖 `format/lyrics/cache/normalizeTrack` 与小程序纯函数回放，**HTTP 层、静态白名单、SSRF/URL 校验、Range、登录/登出/凭据、鉴权/CSRF、配置、启动脚本零覆盖**——恰好是本次问题最集中的区域。`tests/run.mjs:134-140` 名为「等待方收到同一报错」的断言用 `.slice(0,1)` 只检查了第一个等待方。`package.json:10` 的 check 只检查 4 个文件。因此「测试全绿」不能作为发布门禁；双 `onLaunch` 这种初始化缺陷正是测试桩跑不出来的类型（`踩坑与复利.md:215-225` 已有同类教训）。

### 6.6 文档已经失去契约价值
README/ARCH/API 之间关于「上游是谁」「绑哪里」「check 检查什么」「评论返回什么字段」互相矛盾；`踩坑与复利.md` 里已明确写下的安全结论（必须只绑 loopback）被后续代码推翻；`项目评审与改进方案.md` 里 2026-11-04 列的 8 类问题，有些已修（XSS、ARIA、状态机、持久化、移动端），有些换了个形式仍在（性能、文案、契约）。**文档漂移本身就是产品风险**：多端并行时，前后端按各自理解的契约开发，漂移会持续产生「玄学 bug」。

## 7. 建议的处理顺序（只排序，不执行）

**第 0 批 · 先做产品决策（决定后面做不做）**
1. 明确最终定位：个人开源自用 / 面向公众产品。前者把「仅本机 + 强制自登录 + 合规免责」做实并放弃小程序上线；后者必须先走官方授权（路径 B）。
2. 据此决定小程序是继续投入、还是收缩为「同 WiFi 的遥控器」并如实说明。

**第 1 批 · 堵安全（半天量级，收益最大）**
3. 移除/默认关闭 LAN 监听，改为显式开关；加 Host 白名单 + `Origin`/`Sec-Fetch-Site` 校验 + 写接口 CSRF token。
4. `finalUrl` 加 `https:` + CDN 域名白名单、拒绝私网/回环/元数据地址、逐跳校验 302；`isAudio` 改 `^audio/`。
5. 凭据 `mode:0o600`、改用 `Cookie` 头传递、区分临时风控与凭据失效、退出时校验删除结果并通知上游、二维码接口加限流与会话绑定。
6. 修 `stop-server.bat`/`start-server.bat` 的端口精确匹配，去掉 `/F` 强杀。

**第 2 批 · 保核心播放**
7. 去掉音频流 20s 硬超时，只对连接/首字节限时；补齐 416 与 Range 校验；音频响应补安全头。
8. 错误分类：`UPSTREAM_*` / `NO_COPYRIGHT` / `LOGIN_REQUIRED` 分开返回，不再伪装成无版权。
9. 修二维码空 key、登录态时序、筛选与「播放全部」、health 的 cookie 字段。

**第 3 批 · 决定小程序是否上线**
10. 按第 4 节最短路径逐条补齐，用**体验版**验收；若不做备案域名/授权，建议直接冻结小程序投入。

**第 4 批 · 体验打磨（纯样式即可拿到大部分收益）**
11. `--text-muted` 提到 ~5.9:1、`.unavailable` 从 0.42 提到 0.7 并加文字线索；统一缓动变量、降级 24s blur 动画；`--player-h` 改 `calc(108px + env(safe-area-inset-bottom))` 并把热区撑到 44px；四个 dialog 补焦点陷阱、把整表移出 live region、slider 补 `aria-valuetext`。

**验收基线建议**：`npm run check` 覆盖全部 JS、补 HTTP/安全层测试；把 README/ARCH/API 与实现对齐并加契约测试；用一份「冷启动 → 榜单 → 播放 3 分钟不中断 → 拖动进度 → 切后台 → 来电 → 切歌 → 刷新恢复」的清单替代「测试全绿」。
